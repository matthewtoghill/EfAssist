# EfAssist — Model diagrams

A plan for a Diagrams tab that extracts and draws the model for the selected `DbContext`.

Status: **research and options — decided, nothing built**. This is the "why" document: the options
that were considered and the reasoning behind each choice. The decisions are recorded in §8.
`DIAGRAMS-IMPLEMENTATION.md` is the actionable build plan and the thing to work from.

Research date: 2026-08-24. Decisions taken 2026-08-24. Verified against the repo as of `238527b`
(Avalonia 12.1.1, .NET 10, `dotnet-ef` 10.0.10).

## 2. Where the model comes from

This is the load-bearing decision. Everything else follows from it.

### 2.1 There is no `dotnet ef` command that dumps the model

Checked the whole EF 10 CLI surface. The closest candidates and why each fails:

| Command | Why it does not work |
| --- | --- |
| `dbcontext info --json` | Provider name, database name, data source. No entities. Already used by `ScriptViewModel`. |
| `dbcontext list --json` | Context names only. |
| `dbcontext scaffold` | Reverse engineering — reads a *database*, writes C# files into the user's project. Wrong direction, and explicitly out of scope per `PLAN.md` §1.4. |
| `dbcontext optimize` | Does emit the complete model — as generated compiled-model C# written **into the user's project**. Writing files into someone's source tree to draw a picture is not acceptable. |
| `migrations script` | Provider-specific DDL. Getting entities back out means writing a SQL parser per provider. |

### 2.2 The reliable source is the model snapshot

EF already writes a complete, machine-generated description of the model to disk, and it is
committed to the repo:

- `Migrations/<Context>ModelSnapshot.cs` — `BuildModel(ModelBuilder)`, the model as of the **last**
  migration.
- `Migrations/<id>.Designer.cs` — `BuildTargetModel(ModelBuilder)`, the model as of **that**
  migration. One per migration.

Confirmed in this repo: `samples/SampleEfApp/Migrations/BlogContextModelSnapshot.cs` and
`20260818140933_InitialCreate.Designer.cs`. Both carry `[DbContext(typeof(BlogContext))]`, which is
how we pick the right file for the selected context — no guessing.

The snapshot is EF's own fluent API, generated by EF's own code generator, and carries everything a
diagram needs:

```csharp
modelBuilder.Entity("EFExamples.Models.Entities.Employee", b =>
    {
        b.Property<int>("Id")
            .ValueGeneratedOnAdd()
            .HasColumnType("int");

        b.HasKey("Id");
        b.HasIndex("CompanyId");
        b.HasIndex("EmployeeId")
            .HasName("IX_Employee_EmployeeId");
        b.ToTable("Employee");

        b.HasOne("EFExamples.Models.Entities.Company", "Company")
            .WithMany("Employees")
            .HasForeignKey("CompanyId")
            .OnDelete(DeleteBehavior.Restrict);

        b.OwnsOne("EFExamples.Models.ValueTypes.Address", "Address", b1 =>
            {
                b1.HasKey("EmployeeId");
                b1.ToTable("Employee");
            });
    });
```

Entities, CLR types, column types, nullability (`IsRequired`), max length, keys, alternate keys,
indexes, table and schema names, foreign keys with principal/dependent and delete behaviour,
navigation names on both ends, owned types, TPH base types and discriminators. That is a diagram.

**Why this is the right source for this app specifically:**

- No build. No database. No connection string — which keeps the connection-string safety problem
  parked in `ROADMAP.md` rather than reopened.
- Milliseconds, not the 10–60s a `dotnet ef` build costs. The whole tab feels instant.
- Trivially cancellable and trivially testable — it is a pure function from text to a model.
- Works offline and on a solution that does not currently compile.
- Bonus: because every `.Designer.cs` holds its own snapshot, "show me the model at migration X" and
  "diff two migrations" become almost free later. Parked in §9, but the extraction shape should not
  foreclose it.

**Honest limitations, and what we do about each:**

| Limitation | Mitigation |
| --- | --- |
| Snapshot is the model as of the last migration, not the current code. Pending model changes are invisible. | Badge it. `ToolsViewModel` already runs `migrations has-pending-model-changes`; reuse it and show "the code has changed since this migration — the diagram is behind" on the Diagrams tab. This is honest and arguably more useful than silently drawing something. |
| A context with no migrations has no snapshot. `AuditContext` in the sample is exactly this case. | Empty state with a clear reason and a link to the Migrations tab. Not an error. |
| Snapshot is the *relational* model. Ignored CLR members, `[NotMapped]` properties and unmapped navigations do not appear. | Correct behaviour for an ER view. For the class view it means the diagram shows the mapped shape, which is what matters here; say so in the tab's hint text. |
| The generated format could change in a future EF version. | It has been stable in shape since EF Core 2 and it is generated code, not hand-written. Parse defensively: unknown fluent calls are skipped, never fatal. Pin fixtures per EF major version in tests. |

### 2.3 The alternative: build and reflect over `IModel`

The accurate-in-all-cases option. Generate a throwaway project that references the user's migrations
and startup projects, uses `Microsoft.EntityFrameworkCore.Design`'s `DbContextActivator` (or the
user's `IDesignTimeDbContextFactory`) to construct the context, and serialises `context.Model`.
This is roughly what EF Core Power Tools' Visual Studio model diagram does.

- **Pro:** the real runtime model. Pending changes included. Value converters, query filters,
  computed columns, everything.
- **Con:** a generated temp project, a NuGet restore, an MSBuild build, and running the user's code.
  Slow, fragile across TFMs and EF versions, and a large amount of new machinery in an app whose
  entire design is "shell out to `dotnet ef` and parse its output".

**Recommendation: do not build this now.** The snapshot gives ~95% of the diagram for ~5% of the
cost. If the "diagram is behind the code" badge turns out to be a real irritation in daily use, this
becomes the upgrade path — and the extraction interface in §3 is designed so it can be swapped in
behind the same `DiagramModel`.

### 2.4 Third-party tools evaluated and rejected as the source

| Tool | Verdict |
| --- | --- |
| [EF Core Power Tools](https://github.com/ErikEJ/EFCorePowerTools) (`efcpt` CLI) | Its Mermaid diagram is a side effect of reverse-engineering *from a live database connection string*, and it writes generated C# into the output folder. Its true model diagram (`AsDgml()`, DGML) is the Visual Studio extension, not the CLI. Both are the wrong shape for us. |
| [Siren](https://github.com/gman-au/siren) (`Gman.Siren`) | Reads a **compiled** migrations assembly or a live SQL Server connection, outputs Mermaid markdown. Needs a build, is SQL-Server-leaning, and is a small single-maintainer project (MIT, ~17 stars). Not a dependency to build a tab on. |
| `EfToMermaid`, `DbToMermaid`, `mermaid-gen` | All need either a compiled assembly or a live database, and all emit Mermaid text rather than a model we can make interactive. |
| [EFCore.Visualizer](https://github.com/Giorgi/EFCore.Visualizer) | Query *plan* visualiser, not a model diagram. Not applicable. |

Worth noting: **Mermaid is a good export format even though it is a bad source.** See §6.

## 3. Extraction — how to parse the snapshot

Two credible options.

### Option A — Roslyn syntax parsing (recommended)

`Microsoft.CodeAnalysis.CSharp`, `CSharpSyntaxTree.ParseText`, then walk `InvocationExpression`
nodes. No compilation, no MSBuild workspace, no semantic model — a syntax-only parse of one file.

- **Pro:** correct on the things that break a line parser. The real-world snapshot above contains a
  method call whose arguments wrap across two lines:
  ```csharp
  .HasForeignKey("EFExamples.Models.ValueTypes.Address",
      "ContractorId")
  ```
  It also contains nested lambdas (`OwnsOne(..., b1 => { ... })`), string literals with escapes, and
  `#pragma` directives. A syntax tree handles all of it by construction.
- **Pro:** the walker is short — group by `modelBuilder.Entity(...)` lambda, then match invocation
  names inside it.
- **Con:** `EfAssist.Core` currently has **zero package references**, and `PROGRESS.md` calls that
  out as a deliberate property. This breaks it.

### Option B — hand-written line parser

Match `b.Property<T>("Name")`, `b.HasKey(...)`, `b.HasOne(...)` etc. off the generated file's rigid
indentation.

- **Pro:** keeps Core dependency-free. Consistent with how the repo already hand-parses
  `dotnet sln list` output and `--prefix-output` lines.
- **Con:** the wrapped-argument case above is a real, observed occurrence in real snapshots, not a
  hypothetical. Handling continuation lines, nested builder scopes (`b1`, `b2`) and quoted strings
  correctly is, incrementally, writing a worse parser than the one in the box.

**Decided: Option A, in `EfAssist.Core`.** The repo's own convention is to prefer the
correct-on-edge-cases option when the sizes are comparable (`ROADMAP.md` makes the same call about
`dotnet sln list` versus a solution-format parser). Core's lack of package references was where the
project had got to, not a rule.

### 3.1 Shape of the extracted model

Plain records in `EfAssist.Core`, `System.Text.Json`-serialisable, no Avalonia and no UI concepts.
This is also the JSON export format (§6), so it is worth getting readable.

```
DiagramModel
  EfVersion            string?      // from modelBuilder.HasAnnotation("ProductVersion", ...)
  ContextName          string
  SourcePath           string       // the snapshot file it came from
  SourceHash           string       // SHA-256, for staleness detection (§5.4)
  Entities             DiagramEntity[]
  Relationships        DiagramRelationship[]

DiagramEntity
  Name / ClrType / Namespace
  Table / Schema
  IsOwned / IsImplicitJoin / BaseType / Discriminator
  Properties           DiagramProperty[]
  Indexes              DiagramIndex[]

DiagramProperty
  Name / ClrType / ColumnName / ColumnType
  IsRequired / IsKey / IsForeignKey / IsAlternateKey / IsShadow
  MaxLength / DefaultValue / ValueGenerated

DiagramRelationship
  PrincipalEntity / DependentEntity
  ForeignKeyProperties[] / PrincipalKeyProperties[]
  PrincipalNavigation? / DependentNavigation?
  DeleteBehavior
  Cardinality          OneToMany | OneToOne | ManyToMany
  IsOwnership
```

Notes:

- **Many-to-many.** EF 5+ skip navigations generate an implicit join entity with no CLR namespace
  (`modelBuilder.Entity("BlogPost", ...)`). Detect it (two FKs, composite key over both, name is the
  concatenation of the two ends) and offer a toggle: draw it as a node, or collapse it to a single
  `ManyToMany` edge. Default to collapsed in the ER view.
- **Owned types.** Nested `OwnsOne`/`OwnsMany` builders become entities with `IsOwned = true` and an
  ownership relationship. Offer a toggle to inline them into the owner's property list, since that
  is how they exist in the table.
- **Shadow properties.** A `b.Property<int>("BlogId")` with no matching CLR member is a shadow FK.
  The snapshot does not distinguish these; treat any property that is only ever an FK and has no
  navigation as a candidate and mark it as such rather than claiming certainty.

## 4. ER diagram or class diagram — both, from one extraction

This does not need to be an either/or, and building two generators would be a mistake.

One `DiagramModel` feeds two **views** that differ only in labelling and edge semantics:

| | ER view | Class view |
| --- | --- | --- |
| Node title | Table name (`Blogs`) | CLR type name (`Blog`) |
| Rows | Columns: `Name  nvarchar(200)  NOT NULL` | Members: `Name : string`, plus navigations `Posts : ICollection<Post>` |
| Key markers | PK / FK / AK / IX badges | PK badge only |
| Edges | FK, labelled with cardinality (`1..*`) and delete behaviour | Association, labelled with navigation names; inheritance drawn separately |
| Inheritance | Flattened — TPH is one table | `HasBaseType` drawn as a generalisation arrow |
| Owned types | Inlined into the owner by default | Composition edge |

So: a two-item toggle in the tab header, defaulted to ER, remembered per workspace. Both are the
same layout engine and the same renderer; only the node content builder differs. Cost of the second
view is roughly an afternoon on top of the first.

**Decided: ship both.** The active view is a toggle in the tab header. Which one opens first is a
persisted user preference, app-wide rather than per workspace — it is a property of how the person
thinks about their model, not of the solution. ER is the default default.

## 5. The tab

### 5.1 Placement and wiring

A fourth `TabItem` in `MainWindow.axaml`, between Script and Tools. New
`DiagramsViewModel` in `src/EfAssist.App/ViewModels/`, constructed in `MainWindowViewModel` alongside
`Script` and `Tools`, following the exact same pattern:

- `Restore(WorkspaceSettings)` / `Store(WorkspaceSettings)` / `Clear()`
- `NotifyTargetChanged()` — added to the existing `NotifyTargetChanged()` fan-out
- `OnActivatedAsync()` — called from `OnSelectedTabIndexChanged`

⚠️ `MainWindowViewModel.OnSelectedTabIndexChanged` currently hardcodes `if (value == 1)` for the
Script tab. Inserting a tab before Tools does not break that, but the magic number is already a trap.
Worth replacing with a `SelectedTab` enum in the same change.

### 5.2 Interaction

All of it is reachable without a graph library, because we own the layout.

| Feature | Implementation |
| --- | --- |
| Pan / zoom | A `MatrixTransform` on the diagram surface. `PointerWheelChanged` scales about the cursor, `PointerPressed`/`Moved`/`Released` pans, plus Fit / 100% / zoom buttons and a percentage readout. **Do not take a dependency on `Avalonia.Controls.PanAndZoom`** — latest is 11.3.0, it depends on `Avalonia >= 11.3.0`, it has been marked deprecated on NuGet, and there is no Avalonia 12 build. This app is on 12.1.1. Hand-rolling it is ~80 lines and removes a version gamble. |
| Click for detail | Hit-test the cursor against the laid-out node rectangles — a linear scan over a list of rects. Selecting a node fills a side panel from the `DiagramEntity`: CLR type, table, schema, every property with its column type and constraints, indexes, and inbound/outbound relationships. All of it already extracted, so there is genuinely more detail to show. |
| Drag nodes | On pointer drag of a selected node, write the new position into the layout. Suppressed when locked. |
| Lock / unlock | One boolean. Locked (the default) means pan and zoom only; unlocked enables dragging. Persisted. |
| Search and highlight | A search box filtering on entity name, table name, column name and index name. Matches get a highlight brush; non-matches dim. "Next match" pans the view to centre it. |
| Hide/show property categories | Checkboxes: keys only / keys + scalars / everything; show FK columns; show shadow properties; show indexes; show column types; show nullability. Each is a re-render, not a re-extract. Persisted. |
| Auto-layout | See §7. A "Re-layout" button that discards manual positions, behind a confirmation since it throws away dragging work. |

### 5.3 Generation and cancellation

Generation is: find the snapshot file for the selected context → read it → parse → layout → render.
On the snapshot path this is milliseconds, so cancellation is close to theoretical — but the
requirement stands and a 500-entity model is a real thing.

The problem: `CommandSession` is built around `IEfRunner` and a child process. Diagram generation is
in-process work. Options:

- **A (recommended):** add `CommandSession.RunLocalAsync(string label, Func<CancellationToken, Task<T>>)`
  — same `IsRunning` gate, same `Cancel` button, same status line, same output console. About 30
  lines, and it makes the one-command-at-a-time invariant hold for diagram work too, which matters
  because generation may want to run `has-pending-model-changes` alongside it.
- **B:** give `DiagramsViewModel` its own `CancellationTokenSource` and its own Cancel button. Less
  shared code to touch, but now there are two cancel buttons and two notions of "busy".

Trigger is always explicit: a **Generate diagram** button. Nothing auto-generates on tab activation
or on context change — matching the `DiscoveryMode.Cached` philosophy already in `Settings.cs`.
Activating the tab with a persisted diagram shows the persisted one.

### 5.4 Persistence

Per workspace **and** per context, because a solution with three contexts wants three diagrams.

- **Where:** `%AppData%/EfAssist/diagrams/<workspace-hash>/<context>.json`. Follows the existing
  `SettingsStore` split — the core `settings.json` stays small, and a 200-entity model plus its
  layout is far too big to sit in the workspace settings file next to `KnownMigrations`.
  `MigrationFiles.Key()` already has the hash-a-path helper; it wants promoting to something shared.
  Note this is **AppData, not temp** — unlike `ScriptCachePath`, this data is meant to survive.
- **What:** the `DiagramModel`, plus node positions, plus the lock flag, plus the view options, plus
  `SourcePath` and `SourceHash`.
- **Staleness:** on load, re-hash the snapshot file. Different hash (or missing file) means the
  diagram is out of date — show a badge and offer Regenerate, but keep showing the old diagram. Same
  principle as `ScriptViewModel.IsStale`: a stale artefact is still readable, it just stops looking
  current. Second, weaker signal: `has-pending-model-changes` says the snapshot itself is behind the
  code.
- **Layout preservation across regeneration:** match old positions to new nodes by entity name, so
  regenerating after adding one entity does not scramble a hand-arranged diagram. New nodes get
  auto-placed; vanished nodes are dropped.

The small pointer that *does* belong in `WorkspaceSettings`: the last selected diagram kind
(ER/class) and view options, so the tab opens as it was left.

## 6. Export

The key design choice that makes this cheap: **compute layout into a list of primitives, then replay
that list per output**. Rectangles, lines, polylines, text runs, markers. Three of the four formats
then come from one replay function.

`SkiaSharp 3.119.4` is **already in the restore graph** transitively via `Avalonia.Skia` — verified in
`src/EfAssist.App/obj/project.assets.json`. Adding an explicit `SkiaSharp` `PackageReference` to
`EfAssist.App` pulls in no new native assets.

| Format | How | Cost |
| --- | --- | --- |
| **PNG** | `SKSurface` at a chosen scale, replay, `SKImage.Encode`. Alternatively `RenderTargetBitmap.Render(control)` after an explicit `Measure`/`Arrange` at full diagram size, which handles the case where the diagram is larger than the viewport. | Small |
| **SVG** | `SKSvgCanvas.Create(bounds, stream)`, replay. Real vector output, opens in every browser, and prints to PDF from there. | Small — same replay |
| **PDF** | `SKDocument.CreatePdf(stream)`, `BeginPage`, replay, `EndPage`. Vector, and can paginate a wide diagram. | Small — same replay |
| **JSON** | Serialise `DiagramModel` with `System.Text.Json`. It is already the persistence format. | Trivial |
| **Mermaid** | Emit `erDiagram` / `classDiagram` text, matching the active view. ~60 lines of string building, and it is the format that pastes into a README, a PR description, or GitHub — where it renders natively. Arguably the highest-value export here. | Small |

Reuse `ScriptViewModel`'s destination logic wholesale: an optional configured output folder, a Save As
dialog when there is none, `LastSaveAsFolder`, suggested filenames, plus Open file / Open folder. That
pattern is already built, already tested, and already familiar to the user.

**Decided: SVG is hand-emitted, not Skia.** A ~100-line text writer over the primitive list, with no
dependency. It produces smaller and far more readable output than Skia (which emits paths, and
converts text to paths depending on font handling), and it can carry entity names as `id` attributes
so the file is inspectable and styleable afterwards. Skia does PNG and PDF only.

## 7. Layout

Needed because nobody wants to hand-arrange 80 entities from a diagonal pile.

| Option | Verdict |
| --- | --- |
| **Hand-rolled layered layout** (recommended) | Rank entities by dependency depth (principal before dependent, break cycles by ignoring back-edges), place each rank in a column, order within a rank to reduce crossings by barycentre, then route edges orthogonally with a small gutter. ~150–200 lines, no dependency, deterministic, and testable as a pure function. Good enough is genuinely good enough here, because **manual dragging is a requested feature** — the auto-layout only has to be a sane starting point, not a finished diagram. |
| **MSAGL** (`AutomaticGraphLayout`, MIT, Microsoft, netstandard2.0) | Real Sugiyama layered layout plus spline edge routing, headless — you feed it a graph and read back node positions and edge geometry, no WPF needed. Better output than we will hand-roll. Costs a dependency in the layout path and an API to learn, and its geometry model is richer than our primitive list wants. A reasonable Phase 2 upgrade if the hand-rolled layout looks bad on a real model. |
| **Graphviz / external `dot`** | Requires an external binary on the user's machine. Rejected outright — the app currently depends on nothing but the .NET SDK. |
| **Mermaid in a WebView** | Layout and rendering free, SVG export free. But Avalonia has no first-party WebView, and the third-party options drag in WebView2 or CEF — enormous, platform-specific, and hostile to the single-file publish and Velopack packaging already working in Phase 6. It also loses native theming, kills the click-to-inspect integration, and dagre gives no node dragging. **Rejected as the renderer. Kept as an export format (§6).** |

**Decided: hand-rolled layered layout in Core**, as a pure function
`DiagramLayout.Compute(DiagramModel, LayoutOptions) -> DiagramLayout`, with MSAGL parked as the
upgrade if the output disappoints. The expected model size is under 100 entities (§8 Q9), which the
hand-rolled layout handles comfortably and which also rules out needing surface virtualisation.

## 8. Decisions

Taken 2026-08-24. These are settled; `DIAGRAMS-IMPLEMENTATION.md` builds on them.

| # | Question | Decision |
| --- | --- | --- |
| 1 | Does `EfAssist.Core` get its first package reference? | **Yes — Roslyn (`Microsoft.CodeAnalysis.CSharp`) goes in Core.** `PROGRESS.md`'s "no package references at all" was a description of where the project had got to, not a rule against ever adding one. So Option A in §3, and no separate `EfAssist.Diagrams` project. `PROGRESS.md` wants its wording corrected so this does not read as a violated principle later. |
| 2 | ER first, or both views? | **Both.** The default view is a persisted user preference, and a button toggles between them at any time. See §4. |
| 3 | Is "reflects the last migration, not current code" acceptable? | **Yes**, with a clear badge on the tab. The snapshot approach in §2.2 stands; the build-and-reflect approach in §2.3 stays parked. |
| 4 | Fallback when a context has no migrations? | **Empty state.** No source-scanning fallback — it would disagree with the ER view about what exists. |
| 5 | `RunLocalAsync` or a private CTS? | **`CommandSession.RunLocalAsync`.** One busy state, one Cancel button, one status line, one console. §5.3 Option A. |
| 6 | SVG: hand-written or `SKSvgCanvas`? | **Hand-written**, for cleaner and smaller output carrying entity names as `id` attributes. Skia still does PNG and PDF. |
| 7 | Mermaid export? | **In scope.** `erDiagram` and `classDiagram`, matching whichever view is active. |
| 8 | PDF pagination? | **One page sized to the diagram.** No tiling. |
| 9 | Biggest model to handle? | **Under 100 entities** is the expected case. So: no surface virtualisation, and the hand-rolled layered layout in §7 is adequate. MSAGL stays parked as the upgrade if a real model looks bad. |

One more decision, from §5.1: **replace the `if (value == 1)` magic number in
`MainWindowViewModel.OnSelectedTabIndexChanged` with a `SelectedTab` enum** as part of this work.

## 9. Deliberately out of scope

- **Editing the model from the diagram.** Dragging a relationship to create an FK would mean writing
  C# back into the user's project. Firmly out.
- **Diagram diffing between two migrations.** Every `.Designer.cs` holds its own snapshot, so this is
  tantalisingly close to free — but it is a second feature with its own UI. Park it; just do not let
  the extraction API assume there is only one snapshot.
- **Cross-context diagrams.** Blocked by the same N-builds problem as the multi-context tree view
  already parked in `ROADMAP.md`.
- **Custom colours per entity, annotations, sticky notes.** Diagram-editor features, not
  model-viewer features.
- **Printing.** PDF export plus the OS print dialog covers it.
- **Virtualisation of the diagram surface.** Ruled out by §8 Q9 — under 100 entities does not need it.
- **MSAGL layout.** Parked as the upgrade path if the hand-rolled layered layout looks bad on a real
  model. §7.
